## 已确认的需求与顺序

用户要求实际实现和验证独立 Bevy 子工程，承接现有机器人的物理控制、本地 ONNX、交互及莫比斯式视觉体验，并实测运行效率与开发效率。

最新顺序是先实现 MicroDuck 的最基础 MVP 闭环，再完善 MicroDuck 的技能、交互及前两张独立地图，后续逐步引入 SaiRobot。每阶段以实际通过的功能为交付依据。

核心工作是物理状态、观测、推理、动作、力矩和物理积分之间的完整链路。MicroDuck MVP 先使用原有 Walk 策略和腿式形态，完成站立、前进、转向、停止、重置、回放及原有机器人外观的对照检查。

后续主要开发环境选用 DGX Spark，以支持长期运行和持续迭代。macOS 与 Windows 仍是目标平台，分别维护项目验证状态。

## 决策及理由

| 决策 | 理由 |
|---|---|
| 首阶段聚焦一个 MicroDuck 闭环 | 用最小的完整对象检验物理引擎、观测器、推理和引擎时序的组合风险 |
| 官方 Bevy/Rapier 发布绑定作为起点 | 复用其 ECS 生命周期、物理同步和现有调试能力；精度和稳定性由实际机器人回归证明 |
| CPU 同步 ONNX 推理起步 | 与现有 CPU 配置对齐，避免额外策略延迟，便于逐步比对观测与动作 |
| 保留有效控制契约和原始资产 | 模型依赖坐标、浮点处理、动作历史及校准结果；这些是行为基线 |
| 先通过控制与画面门槛，再测性能 | 测量结果必须对应可比功能、画质、物理精度和控制行为 |
| 在 DGX Spark 接续长期开发 | 满足用户对长时间运行与持续项目开发的安排 |

任务、计划与交付说明围绕这些已确认目标展开。需求调整直接体现在最终阶段安排中。

## 工程与文档落点

外层目录固定为 `Bevy_Sim2Sim/`。用户指定本轮持久交接文档放在 `docs/`；运行说明放根 README，唯一工程规范保留在根目录。ONNX 及配套原始 JSON 契约允许进入 `assets/game/dynamic_assets/game_data/<module>/`。

其他目录、crate、资产落点及命名按规范执行。临时报告、验证脚本、日志、截图、录像与采样数据放 `.scratch/`，不提交。保留现有 Godot、Unity 基线及用户未提交内容。

交接没有包含凭据、本机个人路径或远程访问密钥。DGX 上的实际仓库路径、Godot 可执行文件与访问方式由接手环境检查确定。

## DGX 接手的第一轮工作

1. 更新仓库，阅读本入口及实施计划，检查工作区和当前规则入口。
2. 核验机器架构、系统、GPU、驱动、Vulkan、窗口或离屏运行条件；记录 Rust 与原生推理库版本。
3. 在 `.scratch/` 中准备当前 MicroDuck Godot 对照环境，定位和生成所需资产，核对模型与 spec 哈希；执行当前代码的实际启动和固定输入实验。
4. 创建最小 Cargo workspace，按计划顺序完成关节、armature、观测、Rust ONNX 和固定步闭环检查。
5. 实现 MicroDuck MVP，按同一输入回放修复控制与接触问题，完成原有外观的固定机位对照。
6. 每阶段提交可运行工程并更新 README 的实际命令、验证状态和遗留问题。

首次运行失败应记录具体命令、版本、输入、输出和最小复现，按 [风险处理顺序](research.md#组合风险与处理顺序) 定位；将已实测通过的部分与待验证部分分别报告。
